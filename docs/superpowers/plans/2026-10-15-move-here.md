# Move Here Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a server-authoritative `Move Here` order that sends the currently scoped and categorized loaded guards to deterministic safe destinations, survives reloads, pauses for combat, and ends in `Waiting`.

**Architecture:** A versioned entity attachment owns each guard's persistent move destination. The public command service is the only writer, a dedicated server ticker owns execution, and a strict C2S endpoint resolves scope/category filters and safe UUID-ordered slots. The client only arms a short-lived placement session and reports the clicked block and face; it never selects guards or final destinations.

**Tech Stack:** Java 25, Minecraft 26.1, Fabric API networking/events/attachments, Guard Villagers integration, JUnit 5, Gradle.

**Spec:** `docs/superpowers/specs/2026-10-15-move-here-design.md`

## Global Constraints

- Follow TDD in every task: add the focused failing test, observe the expected failure, implement the minimum behavior, and rerun the focused test before committing.
- Commit after every task. Stage only files named by that task; preserve unrelated worktree changes, especially the existing untracked `muster_roll.png`.
- Keep command mutation server-side and routed through `GuardCommandService`; client data is untrusted.
- Never force-load a chunk or teleport a guard for this feature.
- Reuse `RallyConfig.routeMoveSpeed()` and the existing ownership, policy-event, scope, and aggregate-feedback conventions.
- Preserve unknown future move-state data until the player explicitly issues a mutually exclusive order.
- Keep English and Brazilian Portuguese translations in parity.

## Review Focus

- A malformed or malicious packet (unknown category/face, excessive distance, unloaded chunk, outside border, invalid Squad) must cause zero guard mutations. Covered in Task 5.
- A Squad deleted between arming and clicking must be rejected by current server state, not the stale client selection. Covered in Task 5.
- A future-schema attachment must survive reads and reject replacement by `Move Here`, while another explicit order may clear it. Covered in Tasks 1 and 3.
- UUID ordering and partial unsafe-slot failure must be deterministic without preventing valid guards from moving. Covered in Tasks 4 and 5.
- Combat pause/resume, reload persistence, arrival into `Waiting`, timeout, item swap, death, disconnect, and `Esc` cancellation must not leave stale transient state. Covered in Tasks 2 and 6.

## Planned File Map

- `order/move/`: persistent state, codec, attachment facade, slot layout/resolution, execution policy.
- `event/MoveOrderTicker.java`: bounded server-side navigation loop.
- `api/command/`: category contract plus API v6 command/result additions.
- `network/MoveHereC2SPayload.java` and `network/MoveHereNetworking.java`: strict wire contract and server orchestration.
- `client/move/`: category screen and short-lived placement controller.
- Existing Ledger, command service, order status, initialization, translations, API docs, roadmap, and smoke-test documentation receive narrow integrations.
